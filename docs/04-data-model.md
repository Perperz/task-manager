# 04 — Data Model Design (MongoDB)

In this section we'll design the database schema for our Task Manager. We'll define two MongoDB collections (Users and Tasks), then build Pydantic models that validate and serialize the data in Python.

---

## 4.1 What is MongoDB?

**MongoDB** is a **document database**. Instead of storing data in rows and columns like a traditional SQL database (PostgreSQL, MySQL), MongoDB stores data as **JSON-like documents** (technically BSON — Binary JSON) grouped into **collections**.

Key differences from SQL databases:

| Concept       | SQL (e.g. PostgreSQL) | MongoDB            |
|---------------|----------------------|--------------------|
| Data unit     | Row                  | Document (JSON)    |
| Group of data | Table                | Collection         |
| Schema        | Fixed (enforced)     | Flexible (optional)|
| Relationships | JOINs                | References / Embed |

Why MongoDB for this project:

- **No fixed schema required** — we can evolve fields without migrations (though we enforce structure with Pydantic on the application side).
- **Documents map naturally to Python dicts and JavaScript objects** — no awkward ORM translation layer.
- **Great for microservices** — lightweight, easy to containerize, and horizontally scalable.

> **Resource:** [MongoDB Manual](https://www.mongodb.com/docs/manual/) — the official documentation covers everything from installation to advanced queries.

## 4.2 Users Collection

Each document in the `users` collection represents a registered user.

**Schema:**

| Field           | Type     | Constraints                          |
|-----------------|----------|--------------------------------------|
| `_id`           | ObjectId | Auto-generated by MongoDB            |
| `username`      | string   | Unique, 3-30 characters, required    |
| `email`         | string   | Unique, valid email format, required |
| `password_hash` | string   | Bcrypt hashed, required              |
| `full_name`     | string   | Optional                             |
| `role`          | string   | `"admin"` or `"user"`, default `"user"` |
| `is_active`     | boolean  | Default `true`                       |
| `created_at`    | datetime | Auto-set on creation                 |
| `updated_at`    | datetime | Auto-set on creation and update      |

> **Never store plain-text passwords!** We hash passwords with **bcrypt** before saving. The original password cannot be recovered from the hash — authentication works by hashing the login attempt and comparing hashes.

**Indexes:**

```javascript
// Unique indexes ensure no two users share the same email or username
db.users.createIndex({ email: 1 }, { unique: true })
db.users.createIndex({ username: 1 }, { unique: true })
```

An **index** is a data structure that makes lookups fast. Without an index on `email`, MongoDB would scan every document to find a match. The `{ unique: true }` option also prevents duplicate values.

**Sample document:**

```json
{
  "_id": "663f1a2b4e7c8d9012345678",
  "username": "johndoe",
  "email": "john@example.com",
  "password_hash": "$2b$12$LJ3m4ks9Fq2nWZz1vRqKxOzXpYvHj8kGfNcB1dT5sQw7rA6yE3uCi",
  "full_name": "John Doe",
  "role": "user",
  "is_active": true,
  "created_at": "2025-05-12T10:30:00Z",
  "updated_at": "2025-05-12T10:30:00Z"
}
```

## 4.3 Tasks Collection

Each document in the `tasks` collection represents a single task.

**Schema:**

| Field         | Type            | Constraints                                      |
|---------------|-----------------|--------------------------------------------------|
| `_id`         | ObjectId        | Auto-generated by MongoDB                        |
| `title`       | string          | Required, 1-200 characters                       |
| `description` | string          | Optional, max 2000 characters                    |
| `status`      | string          | `"todo"`, `"in_progress"`, or `"done"`, default `"todo"` |
| `priority`    | string          | `"low"`, `"medium"`, or `"high"`, default `"medium"` |
| `assigned_to` | ObjectId (ref)  | References `users._id`, optional                 |
| `created_by`  | ObjectId (ref)  | References `users._id`, required                 |
| `due_date`    | datetime        | Optional                                         |
| `tags`        | array of strings| Optional                                         |
| `created_at`  | datetime        | Auto-set on creation                             |
| `updated_at`  | datetime        | Auto-set on creation and update                  |

**Indexes:**

```javascript
// Speed up queries that filter by creator, assignee, status, or sort by date
db.tasks.createIndex({ created_by: 1 })
db.tasks.createIndex({ assigned_to: 1 })
db.tasks.createIndex({ status: 1 })
db.tasks.createIndex({ created_at: -1 })   // -1 = descending (newest first)
```

**Sample document:**

```json
{
  "_id": "663f1b5c4e7c8d9012345679",
  "title": "Set up CI/CD pipeline",
  "description": "Configure GitHub Actions to run tests and deploy on merge to main.",
  "status": "in_progress",
  "priority": "high",
  "assigned_to": "663f1a2b4e7c8d9012345678",
  "created_by": "663f1a2b4e7c8d9012345678",
  "due_date": "2025-05-20T00:00:00Z",
  "tags": ["devops", "automation"],
  "created_at": "2025-05-12T11:00:00Z",
  "updated_at": "2025-05-13T09:15:00Z"
}
```

## 4.4 Pydantic Models

**Pydantic** is a Python library that validates data using type annotations. When data comes into our API (from a request body, a database read, etc.), Pydantic checks that every field has the correct type and satisfies any constraints we define. If validation fails, it returns a clear error message automatically.

We use **Pydantic v2** syntax throughout this project.

### User Schemas

Create `services/backend/app/schemas/user.py`:

```python
from datetime import datetime
from typing import Optional

from pydantic import BaseModel, Field, EmailStr, ConfigDict


class UserCreate(BaseModel):
    """Schema for creating a new user (registration request body)."""
    username: str = Field(..., min_length=3, max_length=30)
    email: EmailStr
    password: str = Field(..., min_length=8, max_length=100)
    full_name: Optional[str] = None


class UserResponse(BaseModel):
    """Schema for returning user data to clients. Never includes password_hash."""
    id: str = Field(..., alias="_id")
    username: str
    email: EmailStr
    full_name: Optional[str] = None
    role: str = "user"
    is_active: bool = True
    created_at: datetime
    updated_at: datetime

    model_config = ConfigDict(
        populate_by_name=True,
        from_attributes=True,
    )


class UserInDB(UserResponse):
    """Schema for internal use — includes the hashed password."""
    password_hash: str


class Token(BaseModel):
    """Schema for the JWT token response."""
    access_token: str
    token_type: str = "bearer"


class TokenData(BaseModel):
    """Schema for decoded JWT token payload."""
    user_id: Optional[str] = None
```

### Task Schemas

Create `services/backend/app/schemas/task.py`:

```python
from datetime import datetime
from typing import Optional, List

from pydantic import BaseModel, Field, ConfigDict


class TaskCreate(BaseModel):
    """Schema for creating a new task."""
    title: str = Field(..., min_length=1, max_length=200)
    description: Optional[str] = Field(None, max_length=2000)
    status: Optional[str] = Field("todo", pattern="^(todo|in_progress|done)$")
    priority: Optional[str] = Field("medium", pattern="^(low|medium|high)$")
    assigned_to: Optional[str] = None
    due_date: Optional[datetime] = None
    tags: Optional[List[str]] = None


class TaskUpdate(BaseModel):
    """Schema for updating a task. All fields are optional."""
    title: Optional[str] = Field(None, min_length=1, max_length=200)
    description: Optional[str] = Field(None, max_length=2000)
    status: Optional[str] = Field(None, pattern="^(todo|in_progress|done)$")
    priority: Optional[str] = Field(None, pattern="^(low|medium|high)$")
    assigned_to: Optional[str] = None
    due_date: Optional[datetime] = None
    tags: Optional[List[str]] = None


class TaskResponse(BaseModel):
    """Schema for returning task data to clients."""
    id: str = Field(..., alias="_id")
    title: str
    description: Optional[str] = None
    status: str = "todo"
    priority: str = "medium"
    assigned_to: Optional[str] = None
    created_by: str
    due_date: Optional[datetime] = None
    tags: Optional[List[str]] = None
    created_at: datetime
    updated_at: datetime

    model_config = ConfigDict(
        populate_by_name=True,
        from_attributes=True,
    )
```

## 4.5 Relationship Between Collections

MongoDB does **not** have JOINs like SQL databases. When a task has `assigned_to: "663f1a2b4e7c8d9012345678"`, that string is just a reference to a document in the `users` collection — MongoDB won't automatically fetch the related user for you.

In our application, we handle this in the backend code:

1. Fetch the task document from the `tasks` collection.
2. If `assigned_to` is set, make a second query to the `users` collection to get that user's name.
3. Return the combined data to the frontend.

This is called **manual referencing** and is the standard pattern in MongoDB. For our app this is perfectly fine — we only need to display the assignee's name on a task card, so the extra lookup is trivial.

> **When would you embed instead of reference?** If data is always read together and rarely updated independently (e.g., an order with its line items), embedding the sub-documents inside the parent is more efficient. Our users and tasks are independent entities that change separately, so references are the right choice.
